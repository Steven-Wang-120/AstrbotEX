## 2. 后续 MVP 要回答的问题

1. PyRoKi 能否从实时关节状态出发，生成可执行的机械臂 IK 与避障轨迹？
2. 经典导航能否让等效履带车根据雷达观测绕过随机障碍物并到位？
3. 经典感知、几何抓取、规划和反馈控制组合后，能否完成规定的抓取放置任务？
4. RGB + 2D 雷达在哪些场景足够，视觉模块必须提供哪些几何量及误差范围？
5. JEV 能否在延迟预算内改善候选选择，并在变化发生后完成停止、重规划和继续执行？

这里有三个不同结论：`PYROKI_ARM_PASS`、`CLASSICAL_NAV_PASS` 和 `NO_NN_PICK_PLACE_PASS`。分别给出证据，不把整条链都称为 PyRoKi 的能力。

“无神经网络能够完成这个限定任务”可以由纯经典基线支持。引入 Laya 后，系统包含学习式评分，但仍可不使用神经网络生成轨迹或力矩。分别报告 `CLASSICAL_BASELINE` 与 `JEV_ASSISTED`，不混用结论。

## 3. 已核对的技术边界

### 3.1 PyRoKi 是机械臂规划候选，不承担整套系统

官方实现支持 URDF 运动学、IK、碰撞代价/约束和轨迹优化。官方同时明确未提供采样式规划器，碰撞表示也存在近似。[项目说明](https://github.com/chungmin99/pyroki/blob/main/README.md)

Mobile IK 示例优化底座平面位置、朝向和机械臂关节。它没有同时给出小车从当前位置绕过障碍物的可执行路线。首版固定底盘后求机械臂轨迹，底盘路径交给 Nav2。[Mobile IK 源码](https://github.com/chungmin99/pyroki/blob/main/examples/03_mobile_ik.py)

不要机械复制用户参考方案里的旧限制列表。当前源码已有 Box，轨迹示例使用关节/速度约束及世界碰撞 swept-volume 检查。README 的几何列表与源码不完全同步，实施时以固定版本的实际接口为准。[轨迹示例](https://github.com/chungmin99/pyroki/blob/388e43e1fc0d0ee382968d3dd72970fd62a0450c/examples/07_trajopt.py)

### 3.2 “代替神经网络”需要按模块判断

| 模块 | 第一版方法 | 是否先训练神经网络 |
| --- | --- | --- |
| 物体识别与定位 | RGB 颜色/轮廓、已知几何、平面约束 | 否 |
| 抓取候选 | 顶抓规则、物体尺寸、少量夹爪朝向候选 | 否 |
| 机械臂 IK/轨迹 | PyRoKi | 否 |
| 底盘路径 | Nav2 的经典规划与跟踪 | 否 |
| 关节跟踪 | 限速的关节轨迹与驱动反馈 | 否 |
| 夹取保持 | 有限夹紧力、物理接触与摩擦 | 否 |
| 任务顺序 | 小型状态机 | 否 |

SciSpace 检索到的对象中心任务与运动规划研究，在仿真及实物抓放中展示了规划与反馈控制的组合。这支持路线可行性，但不能替代本项目的传感器和接触实验。[原论文](https://arxiv.org/abs/1911.04679)

若后续困难集中在未知物体、遮挡或纹理变化，优先替换感知或抓取候选模块。不要因一个感知失败就把整套执行器改成强化学习策略。

## 4. 推荐机器人与组件

### 4.1 首选一套机器人，避免重复适配

建议首选 **xArm6 + 平行夹爪 + 等效差速底盘**。xArm 的公开 ROS 2 仓库提供机器人描述、夹爪组合和 Jazzy 分支。Isaac 5.1 资产目录也列出 xArm6 与夹爪。[厂商仓库](https://github.com/xArm-Developer/xarm_ros2)。[Isaac 5.1 资产](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/assets/usd_assets_robots.html)

这是适配候选，不是已验证的 PyRoKi–Isaac 联合模型。首先核对 URDF/USD 的关节顺序、轴向、零点、TCP、限位和夹爪 mimic 关系。资产目录中包含夹爪关节的总 DOF 数，不能直接作为机械臂控制维度。

如果 xArm6 的模型一致性或夹爪适配出现明确阻塞，备选 UR5/UR5e + 平行夹爪。PyRoKi 有 UR5 轨迹示例，UR 官方描述仓库支持 Jazzy。只适配一个最终模型，不把两个候选都完整验收。[UR 描述](https://github.com/UniversalRobots/Universal_Robots_ROS2_Description)

首轮不先做一套 Panda 再换 6 自由度机械臂。公开描述/软件与厂商 USD 资产分别记录来源和版本，不把所有可下载资产统称为开源硬件。

### 4.2 底盘模型

底盘使用刚体车架和左右驱动组。通过轮组驱动和物理接触移动，履带外壳用于外观。不逐帧写机器人世界坐标来伪装行驶。

在后续 MVP 平地低速场景中，采用差速运动近似。导航时机械臂收拢。规划 footprint 包含收拢机械臂和传感器外轮廓。首版可采用保守外接圆，避开狭窄通道问题。

这能验证导航接口和移动操作顺序，不能据此验证履带牵引、爬坡、越障或真机里程计误差。

## 5. 感知下限与视觉接口

### 5.1 RGB + 2D 雷达：有条件地支持第一版

PyRoKi 需要机器人状态、目标几何和障碍几何。它不要求某一种传感器，也不直接把图像变成抓取位置。

首轮使用 RGB + 2D 雷达可以验证当前限定任务，但要明确以下条件：

- 平地障碍必须与雷达扫描平面相交。场景不包含未建模的悬空横梁、低矮障碍或地面坑洞。
- 操作台高度、几何和工作区边界作为显式先验。RGB 从标定、已知物体尺寸和平面约束恢复尺度。
- 随机目标和桌上障碍使用已知几何，位姿从 RGB 估计。不能把随机生成器的真值当作感知结果。
- 导航时机械臂收拢，导航 footprint 覆盖整车收拢外形。机械臂操作时底盘停稳。
- 关节反馈、短程里程计和 TF 仍然必需。两种外部传感器不代替机器人本体状态。

| 场景 | RGB + 2D 雷达能否承担首轮 | 需要补齐的信息 |
| --- | --- | --- |
| 平地绕过落地箱体/柱体 | 可以 | 扫描高度、底盘 footprint、里程计、障碍余量 |
| 已知桌面上抓取可见方块 | 可以 | 相机标定、桌面平面、物体尺寸和朝向约束 |
| 已知夹具形成的窄间隙 | 可以尝试 | 夹具三维几何、定位误差、整条机械臂和携物扫掠体 |
| 随机未知高度的桌上障碍、堆叠、悬空障碍 | 不能仅凭当前观测确认可行 | 多视角或深度观测，或明确、可信的几何先验 |
| 遮挡后目标位置不确定 | 当前帧不能直接执行 | 重新观察或返回感知不足 |

这些是传感器可观测性的工程判断。二维扫描的空白不代表机械臂三维空间为空。最低传感器成本通常意味着更强的场景先验。

先在上述允许范围内验证 RGB + 2D。只有失败主要来自缺失三维观测时，才在相同失败场景中增加深度来源。3D 雷达也需要核对近距离分辨率，不能默认它足以解决小物体精定位。

### 5.2 保留的 3D 雷达升级路线

将点云通过 `PointCloud2` 发布。过滤地面和机器人自身点，按高度及体积形成障碍表示。Nav2 voxel layer 可接收 PointCloud2，并将三维占据信息投影到导航代价地图。[Isaac RTX 雷达](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/ros2_tutorials/tutorial_ros2_rtx_lidar.html)。[Nav2 voxel layer](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/costmap_2d/costmap_plugins/voxel/)

首轮场地小且边界已知。导航使用轮组反馈积分的短程里程计，初始坐标对齐已知。随机障碍必须来自雷达观测，不能从场景生成器读取其真实坐标填入规划器。

不把这套配置称为完整 SLAM。若短程里程计漂移成为主要失败因素，再补雷达定位。初期不同时建设三维建图、定位和导航全栈。

操作区点云还用于桌面和近场障碍估计。保留三维高度，不能把底盘用的二维栅格当成机械臂完整碰撞世界。首轮用球、胶囊或盒体近似观测障碍并加余量。

随机障碍优先使用雷达易观测的箱体/柱体。未观测的机械臂扫掠区域不自动认作空闲。无法获得足够观测时，移动到底盘候选观察位或拒绝该次操作。

### 5.3 RGB：目标识别与抓取位置

相机固定安装在能看到桌面及夹爪工作区的位置。颜色用于识别指定物体，轮廓用于估计平面方向。已知尺寸与桌面平面提供尺度约束。

第一版采用“相机射线与已估计桌面/物体顶面求交”，或对具备可识别角点的已知物体使用 PnP。PnP 需要三维点、对应图像点和相机标定，不能只输入检测框中心就得到任意三维位姿。[OpenCV PnP](https://docs.opencv.org/4.10.0/d5/d1f/calib3d_solvePnP.html)

3D 雷达主要负责环境与平面。不要默认它能为每个 RGB 像素提供深度，也不要把传感器方案悄悄改为 RGB-D。目标处点云太稀疏时，使用已知几何约束，或重新观察。

必须记录相机内参、雷达/相机外参、TF 和图像/点云时间。底盘停稳后重新观察，再把目标转换至机械臂基座坐标，避免沿用行驶前的抓取位姿。

### 5.4 交给视觉模块的参数清单

| 类别 | 必须明确的内容 | 由谁提供 |
| --- | --- | --- |
| 固定标定 | 相机内参/畸变、相机至底盘外参、机械臂基座和 TCP、雷达扫描平面 | 机器人与传感器配置 |
| 场景先验 | 支撑平面及误差、已知几何尺寸、固定夹具、允许操作区域 | 场景配置，注明先验来源 |
| 在线物体 | ID、类别/颜色、米制位置、可观测朝向、尺寸、可见性、位姿误差估计 | 视觉感知 |
| 在线障碍 | 几何位置、覆盖区域、未知区域、最近观测时间 | 雷达/视觉感知 |
| 本体状态 | 按名称排列的 q、dq、夹爪开度、底盘位姿与速度、持物状态 | 状态反馈 |
| 任务约束 | 抓哪个物体、放哪个区域、位置容差、朝向自由度、允许接触对 | 上游技能请求 |

控制端内部感知输出采用 `SceneSnapshot`，不要求上游所有插件统一业务 schema：`scene_id / stamp / frame_id / objects / obstacles / support_plane / coverage / uncertainty`。状态快照单独携带 `state_id`，以时间戳和 TF 对齐。接收端记录单调时钟时间，用于过期判断。

首版不强制复杂概率模型。先报告验证集测得的位置/角度误差上界及其适用条件。类别置信度不能替代米制定位误差。缺少关键尺度、TF 或工作区覆盖时，返回 `INSUFFICIENT_OBSERVATION`。

视觉模块可以只估计当前任务需要的自由度。例如直立圆柱的绕轴角度可标为自由，方块顶抓允许数个等价夹爪方向。不要把不可观测角度伪造成精确的六维位姿。

窄间隙先做误差预算：可用间隙必须覆盖定位误差、标定误差、跟踪误差、几何近似误差和停止扫掠余量。不能只用“检测到了物体”作为开动条件。

视觉团队的交付先固定三项：任务需要哪些可观测自由度、在工作区内的米制误差、结果更新周期与最大年龄。控制侧依据这些误差确定间隙和速度，避免先承诺毫米级任务，再要求感知无条件满足。

### 5.5 真值使用边界

单臂调试阶段可以使用物体真值，明确标为 `ORACLE_POSE`。它只隔离规划和接触问题。

正式评估标为 `SENSOR_POSE`。规划器只接收传感器估计、机器人反馈和任务给定的操作台区域。物体、随机障碍和底盘世界真值只供独立评估器使用。

最终报告分别给出 ORACLE 与 SENSOR 结果。传感器挂在机器人上但规划仍读取真值，不能算感知闭环通过。

## 6. PyRoKi 接入中必须处理的细节

### 6.1 起点必须是实际关节状态

官方 `_trajopt.py` 先对起点和终点末端位姿求 IK，再用两个 IK 解构建轨迹。起点末端位姿相同，不保证关节构型相同。[官方实现](https://github.com/chungmin99/pyroki/blob/388e43e1fc0d0ee382968d3dd72970fd62a0450c/examples/pyroki_snippets/_trajopt.py)

适配器使用 `q_start = 最新 JointState` 作为轨迹起点约束。末端目标只用于终点 IK。发出轨迹前再次检查机器人当前 q 与计划起点一致，计划过期就重新求解。

### 6.2 PlanResult 不能只有 success 和关节数组

```text
PlanResult
  status / failure_reason
  joint_names
  positions[] / time_from_start[]
  start_state_stamp / scene_stamp / planning_frame
  target_tcp_pose
  position_error / orientation_error
  joint_limit_ok / velocity_limit_ok / collision_check_ok
  solve_time / cold_or_warm
```

以检查结果决定是否执行，不把优化器返回数组等同于成功。四元数显式转换 ROS `xyzw` 与 PyRoKi 示例的 `wxyz`。关节按名称映射。

先检查轨迹时间严格递增、起点、关节限位和速度。对轨迹段进行扫掠或足够密的碰撞检查，不能只看离散节点。几何近似会漏掉的碰撞由物理执行再次验收。

### 6.3 抓取与携物碰撞

首轮每个物体生成少量顶抓候选，例如 4 个夹爪朝向。先筛掉张口不够和不可达候选，再进行避障规划。最多测试 4 个候选，失败返回原因，不无限重试。

分段规划：预抓取 → 接近 → 闭爪 → 抬升 → 移至放置区 → 放下 → 开爪 → 撤离。只有预期的手指与目标物接触可以在相应阶段放行，不全局关闭碰撞。

抬升后，在规划碰撞模型中加入被抓物体的外形。这个附着只属于规划表示。物理仿真中仍靠夹爪接触和摩擦持物，不能用隐藏 fixed joint、吸附或 teleport 代替平行夹爪抓取。

PyRoKi 轨迹优化失败可能来自初值、模型、碰撞近似或局部解。它不自动等于“无路径”，更不自动意味着“必须使用神经网络”。首轮只处理简单障碍，复杂拓扑的采样式规划作为后续选项。

### 6.4 运行环境

PyRoKi 当前包元数据为 Python >=3.10，依赖 JAX 和 Git 来源的 jaxls。README、文档的 Python 推荐版本并不完全一致。[包元数据](https://github.com/chungmin99/pyroki/blob/main/pyproject.toml)

建议使用独立 Python 3.12 规划环境，先用 CPU JAX。保留 Isaac 的 Python 3.11 和现有 ROS 环境。以一个薄的请求/响应边界连接规划进程与 ROS，不把 JAX 安装进当前 Isaac Conda 环境。

固定 PyRoKi、jaxls 和模型版本。记录冷启动编译与热启动求解时间。障碍数量采用固定上限和有效标记，减少形状变化造成的重新编译。超过上限时合并保守包围体或拒绝规划，不能静默丢掉障碍。

## 7. EX 调度、控制端 Laya 与 ROS 的边界

```text
固定任务脚本，后续替换为 A.E.B.
        ↓ 正式 GoalSubmit + 固定动作参数
EX GoalManager / DecisionService（首轮 MockBackend）
        ↓ Dispatcher → Actor → 控制插件
RGB + LaserScan → SceneSnapshot ─┐
JointState / odom / TF ──────────┼→ Grounder / PyRoKi → 1–4 条候选
控制插件内部 SkillRequest ───────┘                  ↓
                                  rule 或控制端 LayaAdapter
                                                   ↓
                            SafetyGuard → ROS 2 网关 / 标准 Action
                                                   ↓
                                  Controller → Isaac 物理运动
                                                   ↓
                         实际反馈 / 独立判据 → 插件 report → Ledger

STOP / watchdog ─────────────────────→ 最终执行端，不等待模型
```

EX 核心的云端 Jev 与控制端 Laya 是两个不同角色。`c9624a4` 的 Jev 始终 `execution_allowed=False`，只能 disabled/shadow；不能通过 B08/B09 按钮放开。首轮选择已有 MockBackend(kind="start") 调度唯一授权宏动作；动作执行期间由框架保持与取消，模型不续租。

冻结 GoalSubmit 为每个 action_id 提供一份固定参数，EX 候选也没有每条轨迹的独立参数字段。上游只提交语义抓放动作；控制插件内部生成和选择轨迹，不把候选集塞入冻结 DecisionSnapshot。

任务脚本通过已有可信 `submit_goal/renew_goal/cancel_goal` 方法提交正式合同。现有外部 ZMQ 接线尚未完成，首轮不借旧 proposal 入口绕过可信 Goal 服务，也不为此实现 A.E.B. 工作树。

Laya 不能更换目标、扩大工作区或提高 effort 上限。Goal 替换、取消、会话/config/环境/插件代次变化时，插件使旧候选和待执行结果失效。所有结果以 command_id 和执行版本关联。

机械臂采用受限关节位置轨迹；接口为 FollowJointTrajectory 与 GripperCommand，底盘后续使用 NavigateToPose。EX 原生 facade 的发布/订阅经薄网关连接标准 Action，不在插件中私建 ROS executor。Action 接受目标不等于物理成功。

底盘停止输出零速度。机械臂减速后保持，夹爪按持物状态保持有限夹紧力；不能照搬 CartPole 的结束全部零力。


### 7.1 SafetyGuard 必须覆盖最终执行通道

现有 legacy `safety.py` 主要限制底盘速度与持续时间，并响应 estop。新 B02/B04 增加了命令授权和生命周期门禁，但仍不等于机械臂最终驱动 effort 检查。机械臂保护放在项目 R 的最终执行通道。

本 MVP 在新机器人的最终执行适配中落实保护，不为此重构全部旧插件。

| 层次 | 最小检查与行为 |
| --- | --- |
| 执行前 | 数值有限、关节/速度/加速度范围、碰撞、状态新鲜度、轨迹起点、允许接触、机器人配置版本 |
| 显式 effort 控制 | 对最终总输出检查和限幅，包括反馈与前馈。无效输入触发停止，持续饱和返回执行失败 |
| 位置/速度控制 | 检查轨迹目标，并配置 Isaac drive 的最大 effort。只限制消息中的 effort 字段不够 |
| 执行期间 | 每个控制周期检查状态超时、跟踪误差、停止锁存与命令有效期 |
| 物理记录 | 分开记录请求 effort、最终命令 effort、驱动实际 effort。关节反力/接触冲量单列 |

旋转关节 effort 单位是 N·m，直线关节是 N。上限来自当前模型和 actuator 配置。JEV 和任务请求不能提高上限。Isaac 文档提供驱动力限制；ROS 轨迹控制器在 effort 模式下还可能叠加反馈输出。[Isaac drive 调参](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/robot_setup_tutorials/joint_tuning.html)。[ROS 轨迹控制器](https://control.ros.org/jazzy/doc/ros2_controllers/joint_trajectory_controller/doc/userdoc.html)

执行前可以拒绝明显超限的 effort 请求。但对位置轨迹，若没有完整动力学及接触预测，就不能预先证明全程所需力矩。首轮用限速、限加速度、驱动硬上限和跟踪监测实现受限执行。若限幅后无法完成任务，则返回失败，不自动提高上限。

驱动 effort 上限不等于所有碰撞反力都有同样上限。必须注明测量语义。若实际驱动 effort 无法读取，记录为未知，只能宣称命令/配置限制通过。

### 7.2 可中断与停止

停止入口放在执行进程。规划与 JEV 在其他进程运行。GUI 按钮、取消请求或 watchdog 均可触发停止，不能排在一次长推理后面等待处理。

停止时取消活动目标，增加 `execution_epoch`，使旧轨迹、旧评分和队列命令失效。底盘受限减速，机械臂受限减速后保持，夹爪按持物状态保持有限夹紧力。恢复需要新的有效执行请求，旧队列不能自行恢复。

“随时可发起停止”不等于机器人能瞬间静止。记录请求到接收、旧命令失效、开始制动、实际停稳四个时点，以及停止期间位移。正常停止也必须满足 effort 上限和可用停止空间。

watchdog 使用单调墙钟，避免仿真暂停冻结超时检测。Isaac 卡死时外部进程不能保证继续执行物理减速，仿真暂停属于独立兜底，不计作控制器停止通过。

底盘避碰优先复用 Nav2 Collision Monitor，置于速度输出链最后。停止锁存、关节保护和命令过期检查复用同一个执行适配。[Nav2 官方接法](https://docs.nav2.org/jazzy/tutorials/general_tutorials/using_collision_monitor/using_collision_monitor/)

## 9. 第一个完整演示

场景为一块平地和一个操作台。任务给出操作台区域及目标物颜色，不给出随机物体与障碍真值。物体和放置区在同一操作台上。

```text
车体从起点出发
→ 雷达观测随机箱体/柱体
→ Nav2 绕障到操作台附近
→ 线速度和角速度降至停车阈值
→ RGB 重新定位指定物体和放置区
→ 选择预抓取位姿及夹爪方向
→ PyRoKi 生成从当前关节状态开始的轨迹
→ 机械臂接近，夹爪闭合
→ 物体抬升并保持
→ 搬运到同台放置区，放下并开爪
→ 夹爪撤离，物体留在区域内
→ 输出任务结果
```

首轮不携物跨区域行驶。这样已经覆盖底盘导航、机械臂规划、感知定位和物理抓放，同时避免再引入携物底盘稳定性。

操作台周围预设少量可选停车位。Nav2 判断可达性，PyRoKi 判断操作可达性。最多尝试 3 个停车位，不把全身联合优化放进第一版。

最终选一个冻结评估工况在 GUI 中运行，同时显示 RGB 和雷达/代价地图。它计入正式评估，不额外重跑一整套录像工况。

## 10. MVP 场景与通过标准

以下是建议的初始配置，实施前写入实验配置。它们不是实测成绩。依据最终模型尺寸完成一次调整后冻结，不在看到评估失败后临时放宽。

- 单次一个目标物，首版优先 4–6 cm 方块。物体必须在夹爪开度和载荷能力内。
- 每轮约 5–8 个静态障碍，位置随机。生成器避免初始穿透，并保留基本操作空间。
- 规划器看不到随机种子对应的障碍真值。生成规则可以保证大类任务可行，但不能把解路径注入导航。
- 机器人低速运行。底盘速度先限制在 0.15 m/s，机械臂速度按模型限位取保守比例。

| 指标 | 首版建议判据 |
| --- | --- |
| IK/FK | 末端位置误差 ≤5 mm，受约束的朝向误差 ≤5° |
| 导航到位 | 位置误差 ≤0.10 m，朝向误差 ≤10°，并通过后续可达性检查 |
| 停车 | 实测线速度 ≤0.02 m/s、角速度 ≤0.05 rad/s，连续 0.5 秒 |
| 机械臂执行 | 关节/速度限制满足，无长期跟踪误差，无非预期碰撞 |
| 抓取 | 目标真实抬升至少 8 cm，持续 1 秒，期间没有依靠外部附着 |
| 放置 | 开爪并撤离后，物体仍在指定区域，稳定至少 1 秒 |
| 演示通过 | 10 个冻结可行场景至少 8 个完整成功，全部结果保留 |
| 失败处理 | 不可达和封路两个场景均返回有原因的失败，不伪报成功 |

10 次试验是 MVP 初筛，不是可靠性认证。碰撞、掉落、超时和拒绝执行均记录，不能把失败从分母中删除。真实发生的非预期碰撞不能因总成功率达标而被忽略。

独立评估器可以使用仿真真值判定抬升、落点和碰撞。规划与控制不能读取这些评估真值。接触判定区分手指/目标的预期接触和机器人/环境的非预期接触。

## 11. 如何决定是否引入神经网络

| 观察到的结果 | 后续结论或下一步 |
| --- | --- |
| ORACLE 和 SENSOR 均稳定通过 | 当前限定任务不需要先训练抓取控制策略，继续经典方案 |
| ORACLE 通过，SENSOR 经常失败 | 先定位标定、遮挡和物体位姿误差，必要时只引入学习式感知 |
| 位姿正确，但夹取经常滑脱 | 先检查夹爪几何、接近方向、摩擦和驱动力，再判断是否需要抓取质量模型 |
| IK/轨迹经常失败，执行器正常 | 检查可达性、起点、碰撞近似和初值。复杂路径可考虑采样规划 |
| 轨迹有效但关节执行偏差大 | 修正执行适配与驱动，不把问题归因于感知或规划网络 |
| 未知对象、接触丰富任务仍是主要需求 | 单独设计学习式抓取或策略对照，复用现有传感器和执行接口 |

不增加端到端抓取策略训练。本任务已明确要求一次小规模 Laya 微调，按第 20 节实施；必须先完成原始模型的 ROS 2 实际闭环。固定场景、传感器输入和成功规则，只替换评分模块。

更精细不自动意味着神经网络更好。窄间隙首先依赖几何精度、误差余量和可跟踪轨迹。学习式方法可以改善复杂场景中的初值和候选排序。DiffusionSeeder 与 PRESTO 均采用学习式轨迹提案，再由优化器修正。这支持混合路线，但不能证明 Laya 已具备机器人轨迹评价能力。[DiffusionSeeder](https://arxiv.org/abs/2410.16727)。[PRESTO](https://arxiv.org/abs/2409.16012)

PyRoKi 的软件可用性也单独判定。Nav2 成功不代表 PyRoKi 成功，感知失败也不代表 PyRoKi 不可用。

## 12. 最小工程边界与交付

先保留一个仿真入口、一个 PyRoKi 适配器、一个感知适配、一个执行适配、一个顺序任务入口和一个评估器。Grounder 组织这些接口，控制端只增加一个可替换的 LayaAdapter。Nav2 使用现有包，不手写第二套导航。

沿用当前目录分层：仿真放 `sim/`，ROS 组件放 `ros2_ws/src/`，入口放 `scripts/`，文档放 `docs/`。运行数据放共享数据目录的新子目录。Cartesian/TCP、关节名和模型限位由机器人配置描述，避免写死 Panda/UR5 的名称。

每次保存：机器人与软件版本、场景种子、输入来源 ORACLE/SENSOR、传感器/状态时间戳、计划摘要、执行反馈、阶段结果和独立物理判据。

当前 CartPole 已完成的证据保持不变。新任务只复用必要代码，不恢复退休脚本，不让新场景使用 CartPole 的全局话题或实验专用阈值。

人工介入集中在首次 GUI/传感器视角确认、视觉模块接口对接、机器人候选出现实际阻塞时的选型调整，以及最终演示观看。JEV 训练若涉及新增硬件或付费服务，再另行确认。常规参数、运行与阶段提交由执行器处理。

## 14. 开发项目 L：控制端 LayaAdapter

状态：PLAN ONLY，尚未接入。首选 [NandhaKishorM/laya](https://github.com/NandhaKishorM/laya/blob/6d942c92081fbc139e736bbd9ac0023223c29b7f/README.md)，代码基线 `0.3.22`。这是本轮已选定的验证对象，不等于已证明适用于机器人。

### 14.1 目标、复用和限制

开源模型提供文本/JSON 状态与 choice/score/noul 输出。本项目必须自行实现薄适配、异步调用、候选校验与 ROS 连接；这些不由安装 Laya 自动完成。

首版复用已验证的 `convaiinnovations/laya` bundle 中 `typed-decisions`，权重 revision 固定为 `55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851`。抓取/搬运通过 task_kind 区分，不启动四个模型服务。PyRoKi 负责几何轨迹，Laya 选择有效候选，控制器负责跟踪。

官方报告的 T4 短输入延迟不是本机 ROS/Isaac 延迟。choice 概率是模型偏好，不等于物理成功概率；不会用高分跳过碰撞或 effort 检查。

### 14.2 输入输出与 worker

`select(SkillRequest, SceneSnapshot, RobotState, CandidateSet) -> Selection`。

输入带 command_id、request_id、ex_session、goal_revision、execution_epoch、candidate_set_id、robot_config_hash、接收时间及有效期。候选摘要包含单位、阶段、方向、路径长度、预计时长、间隙和不确定度；不包含事后执行标签。

输出带原候选集 ID、候选 ID、评分、模型 revision、实际输入 hash、耗时、execute/hold/replan 或明确错误。hold/replan 不发布新轨迹。选中 ID 必须属于这次有效候选集。

通过固定模型调用 choice，禁用自动多模型路由和执行中下载。首版完整输入 token 预算为 1024，候选最多 4 个；超预算显式拒绝，不静默截掉任务或候选。模型返回的置信度只记录，不先引入未经校准的阈值筛选。

规划/评分 worker 与 ROS 执行进程分开。最多一项 live 请求和一项最新待处理请求；请求超时初值 300 ms。超时不会启动第二个推理副本；迟到响应失效。请求发出后超时、取消或响应不确定时进入 restart_required，拒绝新推理。关闭连接不代表服务端计算停止。必须确认本任务拥有的旧服务已退出，启动并预热新服务，创建新后端，通过可信切换和新的 Goal 授权恢复；不得自动重放。执行端始终保持独立可取消。

### 14.3 开发步骤与验收

| 步骤 | 工作 | 完成条件 |
|---|---|---|
| L1 | 固定依赖与权重，接官方预测接口 | 能读取结构化输入并返回有限、合法输出；冷加载单列 |
| L2 | 映射候选摘要与 choice，记录实际输入 | 输出严格属于候选集，不虚构轨迹；超预算可诊断 |
| L3 | 异步 worker 与版本/截止时间 | 旧结果、超时、崩溃不产生新动作；ROS 回调不阻塞 |
| L4 | 复用项目 R 接原始模型实际执行 | 至少一次可追踪的模型选择经 ROS 2 驱动 Isaac 完成抓放 |
| L5 | 运行 R 的取消/失联/迟到/GUI 工况 | 原始模型 ROS 闭环验收通过后，才进入项目 T 微调 |

局部样例只检查适配，不建独立复现工程。没有足够候选时可以只执行一个有效候选，但“多候选选择通过”必须另有至少两个有效选项及真实模型返回的证据。

故障用例包含未知 ID、空结果、NaN、超预算、超时、worker 崩溃、Goal 替换和取消。默认失败进入停止/保持；诊断性的规则回退必须单独标记 selector，不能计作 Laya 成功。

### 14.4 交付与人工介入

交付薄 Adapter、worker 调用边界、模型/依赖锁定清单及实际输入—选择—执行日志。代码位置沿用项目 A 的单个控制包，不新建推理平台。

人工介入只在本机模型依赖无法满足、需要换模型或新增算力时发生。Laya 没有效果提升也允许如实结束验证；微调计划见第 20 节。


## 15. 正式上游 Contract 与控制端内部输入输出

上游沿用已同步的 `GoalSubmit`：schema_version、request_id、ex_session、task_id、step_id、goal_id、goal_text_en、allowed_actions、parameters[action_id]、completion.required_success_actions、lease_ms 和可选 expected_revision。参数必须通过动作 schema。

控制插件把正式动作参数转换成下面四种内部结构。`SkillRequest` 不是新上游线协议，CandidateSet 不加入冻结的 EX DecisionSnapshot。四种结构位于同一个控制包中，执行使用标准 ROS Action。

| 结构与生产者 | 最小内容 |
| --- | --- |
| `SkillRequest`：控制插件 | 请求 ID、技能/阶段、目标物 ID、目标区域或 TCP 目标、容差、朝向自由度、允许接触、规划时限、成功判据引用 |
| `CandidateSet`：Grounder | 请求/场景/状态 ID、机器人配置版本、执行代次、候选列表、不可行原因 |
| `Selection`：LayaAdapter | 候选集 ID、被选候选 ID、各候选评分、模型版本、耗时、`execute/hold/replan` |
| `ExecutionResult`：执行与评估 | 选中候选 ID、实际结束状态、失败/停止原因、反馈误差、物理成功判据、阶段耗时 |

### 15.1 Grounder 的输入

`ground(SkillRequest, SceneSnapshot, RobotState, RobotProfile) → CandidateSet`

其中 RobotState 必须包含 q、dq、底盘状态、夹爪状态和当前动作阶段。只有结构化图像与关节位置仍不够判断停车、携物和轨迹切换。

RobotProfile 提供固定的模型、TCP、关节/驱动限制和传感器标定版本。上游请求可以收紧约束，不能放宽机器人的硬限制。

请求必须写清抓放成功的含义。例如“红色方块位于区域内、夹爪已打开并撤离、物体稳定 1 秒”。“执行了放置动作”不是成功判据。姿态允许自由的轴要明确，避免 5–6 自由度机械臂承担不必要约束。

### 15.2 Grounder 的输出

每个候选包含两部分：

| 可执行计划，供 Guard/Controller 使用 | 候选摘要，供 JEV 使用 |
| --- | --- |
| 不可变的候选 ID、计划引用及内容标识 | 目标物与任务阶段 |
| 关节名、q(t)、时间、必要的速度/加速度 | 抓取方向、接近方向、少量 TCP 关键点 |
| 起点 q/dq、有效期限、预期动作结束条件 | 路径长度、执行时长、最小间隙、关节余量 |
| 碰撞检查、允许接触、携物几何、限制配置版本 | 位姿误差、可见性、跟踪历史、已知失败特征 |

JEV 读取的是有明确单位的摘要和少量关键点。长轨迹保留在计划对象中，不能把一个路径字符串交给模型后假定它读过全部轨迹。摘要不足以区分候选时，再补少量特征，不先引入视频预测器。

几何有效性由 Grounder 检查，发出动作前由 Guard 对当前状态复核。JEV 不负责从一堆小数重新计算 FK 或碰撞。选中的 ID 必须属于当前候选集，不能现场生成另一条未经检查的轨迹。

### 15.3 一次完整决策

```text
SkillRequest + 场景/状态快照
→ Grounder 生成最多 4 个候选
→ 剔除违反硬约束的候选
→ JEV 在有效候选和 hold/replan 选项中选择
→ Guard 检查候选版本、状态变化和执行权限
→ Controller 执行选中的计划
→ 反馈与独立成功判定
```

快照过期、场景变化影响有效性、起点偏差超限或 STOP 均使原选择失效。普通观测刷新不必每次推翻计划，应检查与当前计划有关的变化。

JEV 超时或输出非法时，由执行器进入受限停止/保持。首版不在评分故障后自动继续旧计划。上游的大模型无需参与每次局部重规划。

## 16. 评分如何参与轨迹优化

首版采用有限候选搜索：改变抓取方向、预抓取距离或一个绕障初值，最多产生 4 个候选。JEV 排序，Controller 执行。每轮只改变少量参数，便于归因。

可以把选择写为：

```text
valid = 满足几何、关节、状态与执行限制的候选
selected = argmax JEV(task, scene, state, candidate), candidate ∈ valid
```

首版每次请求只生成一组最多 4 个候选，不以未校准分数触发递归优化。无有效候选或选择 replan 时，先停稳，再允许基于新状态的一次重新规划；重试计入同一任务时限。

这种方法可以优化候选选择，但不保证找到全局最优轨迹。黑盒评分不能直接当作可微代价塞入 PyRoKi。第一版不开发可微评分、全身 MPC 或多模型递归协商。

执行中的变化先触发停止/停稳，再基于新的 q/dq 规划和评分。后续若停顿妨碍演示，再研究连续轨迹切换。首版必须在日志中把“停下后重规划”与“连续运动中重规划”区分。

## 17. 延迟测量与精细任务

### 17.1 计时口径

分别记录冷启动加载/JIT，以及热运行的感知、Grounder、JEV、Guard、ROS 交接。`T_decision` 从结构化快照可用计到执行器接受新计划。`T_sensor_to_action` 从原始传感器采集计到动作真正开始，覆盖感知处理。两者均使用同一墙钟口径，不能将仿真时间戳直接与墙钟相减。若采集端只有仿真时间戳，先从接收端计时并注明缺少采集/传输延迟。执行完成耗时单列。

使用单调墙钟。JAX 求解必须等待结果实际就绪再停止计时，否则只测到异步提交时间。[JAX 计时说明](https://docs.jax.dev/en/latest/benchmarking.html)

不把仿真时间当计算延迟。记录硬件、软件版本、候选数、障碍数、轨迹节点数、输入 token 数、GUI/传感器状态和仿真实时因子。

| 工况 | 要区分的问题 |
| --- | --- |
| 无障碍、宽松朝向、单候选 | 求解基础开销 |
| 同一目标、收紧位置/朝向容差 | 精度约束带来的开销 |
| 普通障碍、4 个抓取/路径候选 | 候选生成与评分开销 |
| 已知几何的窄间隙 | 初值、碰撞检查、失败重试开销 |
| 执行中目标/障碍发生一次受控变化 | 停止、刷新、重规划与恢复延迟 |
| 故意延迟 JEV 或中断状态反馈 | 超时与停止是否独立生效 |

前四类先各测 30 次轻量规划/评分调用，变化目标或初值，避免只测缓存。复用已有状态快照，不重复执行 120 次完整抓放。后两类各做一次物理故障/变化注入，再按失败原因补测。

报告 p50、p95、最大值、失败率和超时率。失败与超时保留在总数中，另列成功请求的求解耗时，不能只报告成功快速样本。

这组样本用于 MVP 性能筛查，不证明最坏延迟上界。若目标相对夹爪以 0.1 m/s 运动，300 ms 内可变化 3 cm。窄间隙需要低速、最新反馈和独立停止，不能只依靠 JEV 重规划追赶变化。

### 17.2 暂定预算，全部需要实测

| 项目 | MVP 目标 |
| --- | --- |
| 单次 JEV 热评分 | p95 ≤100 ms |
| 简单场景热重规划至执行器接受 | `T_decision` p95 ≤300 ms，包含 Grounder、评分、Guard 和交接。含感知的 `T_sensor_to_action` 另报 |
| 第一次加载/JIT | 在开始运动前完成，时间单列 |
| Controller/最终保护 | 独立周期执行，起步按 100 Hz 级设计并与物理步长匹配 |
| JEV/候选更新 | 事件触发，最高约 5–10 Hz，无需每个控制周期重算 |

这些数值是工程目标，不是已获得的成绩。初次规划和窄间隙规划单独报告。如果全链超过 300 ms，即使 JEV 只花 30 ms，也不能宣称满足该重规划目标。顺序演示可以停稳后等待计划，但必须注明此限制。

最终 GUI 工况同时测时间，包含渲染、传感器与模型竞争。先用 CPU JAX。只有实测发现它是瓶颈时，再尝试 GPU 或减少候选计算。

### 17.3 精细任务的最小扩展

沿用同一机器人和运行器。普通抓放通过后，只加“较小落点容差”和“已知夹具窄通道”两种配置。以夹爪和携物外形定义通道，检查整臂扫掠，避免只检查 TCP。

先用 ORACLE 输入分离规划/跟踪误差，再在相同精细工况中使用 SENSOR 输入。复用原有模式开关，不重建数值验证项目。记录落点误差、最小实际间隙、失败阶段和延迟。

若 ORACLE 已满足精度而 SENSOR 不满足，先改感知。如果候选轨迹有效但跟踪不准，先改控制。如果候选经常卡在局部解，才评估学习式初值或其他规划器。Laya 排序本身不能提高编码器分辨率或消除标定误差。

## 18. 开发项目 A：机械臂经典基线

状态：PLAN ONLY。目标：固定底盘，让已知物体通过 PyRoKi、Guard、ROS 和 Isaac 完成真实抓放。此阶段不加载 Laya，不训练模型。

### 18.1 依赖、复用与缺口

- 复用 CartPole 已验证的反馈时间规则、单执行源原则和 Isaac 启动环境；不移植两关节解析器、LQR 或 5 N 阈值。
- 模型固定为 xArm6 与匹配平行夹爪。核对 URDF/USD/TCP/关节名、轴向、零点、限位、mimic 和碰撞几何；不能按 USD 总 DOF 猜臂关节数。
- 复用 PyRoKi IK/轨迹优化；补实际 q 起点、时间参数、独立几何检查和碰撞阶段规则。
- 依赖项目 R 的最小执行网关和停止能力。A 与 R 共用一次物理基线，不各跑一套抓放。
- B08/B09 不阻塞底层规划器开发；最终 EX 闭环和可视化由同一命令日志接上。

### 18.2 最小代码位置与接口

后续新增一个 `ros2_ws/src/astrex_mobile_manipulation/` Python 包，容纳纯数据结构、Grounder/PyRoKiAdapter、LayaAdapter、worker 和 ROS 网关。worker 在独立 Python 3.12 环境运行，只加载纯 Python/规划子模块，不导入 rclpy；ROS 节点在 Jazzy 环境运行。两者可安装同一包，避免复制合同。

后续仿真入口为 `sim/scripts/run_mobile_manipulation.py`，统一任务入口为 `scripts/run_mobile_manipulation_trial.py`。模型和场景配置放 `config/mobile_manipulation/`。独立 EX 仓库中的控制插件源码放 `plugins/control/astrex_sim_control/`，默认禁用，只加载到隔离测试实例。

接口使用第 15 节内部合同：`ground(SkillRequest, SceneSnapshot, RobotState, RobotProfile) -> CandidateSet`。每个候选关联一份不可变、带 hash 的 PlanResult；无可行解时返回原因，不返回空数组加 success。

### 18.3 开发步骤

| 步骤 | 实现 | 完成条件 |
|---|---|---|
| A1 模型与反馈 | 核对 3 个姿态的 FK/TCP/关节对应；夹爪开闭；读取状态 | 名称/单位一致、有限值、起点来自反馈 |
| A2 单臂规划 | ORACLE_POSE 下可达、不可达、简单障碍；候选最多 4 个 | 有效轨迹有限、时间递增、关节/速度/碰撞通过 |
| A3 受限物理执行 | 项目 R 的同一网关驱动接近、闭爪、抬升、搬运、放置 | 无隐藏附着；达到第 10 节抬升/放置条件 |
| A4 传感器输入 | 切 SENSOR_POSE；标定 RGB、已知几何和平面；3 个开发场景 | 控制端不读取随机对象真值，定位不足可拒绝 |
| A5 精细配置 | 收紧落点范围、增加已知夹具窄间隙 | 同一运行器给出误差、最小间隙和失败阶段 |

规则选择器使用有效候选中的确定性排序：先满足任务容差，再取较短预计执行时间，持平按 candidate_id 排序。保持规则固定，作为模型比较基线。

### 18.4 失败、验收和交接

输入过期、TF 缺失、目标不可观测、无候选、起点偏差过大时，不向控制器发送轨迹。执行偏差、物体掉落或超时终止当前任务，并保留真实失败原因。计划失败不自动等同于场景无解。

证据包含模型/配置 hash、初始状态、候选与拒绝原因、最终执行轨迹、驱动限制、关节反馈和物理结果。A1–A5 使用同一日志，不建立单独数值验证工程。

人工介入：首次 GUI 确认夹爪及相机视角；xArm6 资产无法匹配时再讨论替代机器人。普通参数一次固定后冻结，评估失败不能临时放宽阈值。

## 19. 开发项目 R：ROS 2 执行网关与实际闭环

状态：PLAN ONLY。本次上游 ROS 测试只证明通信能力；机械臂命令、状态、取消、物理结果仍需本项目开发与验收。B11 与本章是同一工作，不重复实现。

### 19.1 复用与边界

复用 EX `context.ros` 的原生发布/订阅、绑定代次、队列与 quiesce。当前 facade 无完整 Action 客户端能力，使用薄网关转换；插件不自行 init/spin ROS，也不扩建通用 Action SDK。

机械臂使用 `control_msgs/action/FollowJointTrajectory`，夹爪使用 `control_msgs/action/GripperCommand`，底盘后续使用 `nav2_msgs/action/NavigateToPose`。Isaac 执行适配提供必要的动作处理与反馈，不导入真机驱动。

插件 start/cancel 回调只受理转交，预算沿用上游默认 20 ms。推理、求解和等待结果不能阻塞 Actor 或 ROS 状态回调。

### 19.2 最小通信合同

EX 与网关使用独立 `/astrex/mobile_mvp` 命名空间，通过现有 facade 支持的原生消息交换。首版采用 `std_msgs/msg/String` 承载严格校验的有界 JSON，避免另建自定义消息包。ROS 内部轨迹仍使用标准 Action。

| 通道 | 内容 | 行为 |
|---|---|---|
| `command` | schema、command_id、ex_session、goal_revision、execution_epoch、deadline、参数/轨迹标识 | reliable/volatile；无 transient 重放；每次只受理一个动作 |
| `cancel` | 同一身份与取消原因 | 独立入口；取消使旧 epoch 失效 |
| `lease` | 活动 command_id、会话/epoch、递增续租序号 | 活动且授权有效时每 100 ms 续租；重复旧序号不能续期 |
| `ack` | 受理/拒绝、原因、执行器会话 | ACK 不等于执行成功 |
| `feedback` | 状态序号、command_id、阶段、误差、关节/夹爪/底盘摘要 | 只保留最新反馈；执行器重启可识别 |
| `result` | 终态、选中候选、物理判据、停止引用 | 一次终态，重复结果幂等处理 |

JSON 上限 64 KiB，队列有界；超预算明确拒绝，不能截断轨迹。完整计划在本机 worker/网关中以 ID 与 hash 关联，模型只读摘要。初版同主机进程使用固定 loopback IPC 连接规划 worker，最多一项活动请求及一项最新待处理请求；不搭建通用任务队列。

对 command_id 保留当前执行器会话内的去重结果。执行器重启后进入无活动命令状态，旧消息不恢复运动；EX 将未确认旧动作保持 unknown/blocked，取得停止证明后才允许新授权。

租期初值 500 ms，状态最大接收年龄 200 ms，ACK 等待上限 1 s；这些是仿真配置，不是硬实时保证。动作结束时限由 Goal 和动作配置中较紧的一项决定。最终执行端每控制周期检查租期，不依赖上游正常发送 stop。

### 19.3 执行与停止

1. 插件验证受理条件，把工作交给异步 worker，返回 accepted。
2. Grounder 生成计划；rule 或 Laya 选择后，由 Guard 用最新状态复核。
3. 网关提交标准 ROS Action，关联外层 command_id 与内部 Goal UUID。
4. 控制器跟踪受限轨迹；网关回报 running、反馈和终态。
5. 独立评估器给出抓放物理结果。Action 成功但物理判据未满足时，任务仍为失败。

Guard 检查目标、模型/config hash、有限值、碰撞、关节/速度/加速度及起点。最新 q 与计划起点容差初值为每关节 0.02 rad；首版只从停稳状态开始新轨迹。状态序号正常递增不会自动使所有候选失效。

普通取消通过正常受控接口。`publish_stop` 仅在现有环境失活授权 hook 中使用，不将其当作通用取消捷径。

停止先失效旧 epoch，再让底盘减速至零、机械臂受限减速后保持；夹爪持物时保持有限夹紧力。关节 `abs(dq) <= 0.02 rad/s` 且底盘满足第 10 节停车阈值，连续 0.5 s，才生成停稳证据。证据包含 command_id、执行器会话和测量窗口引用。

插件只有拿到对应证据，才调用 `context.actions.report(..., stop_evidence=StopEvidence(...))`。unknown/failed/timed_out 后续通过受控 reconcile_stop 释放资源，不把既有终态改写成 canceled。GUI 暂停不能作为停稳证明。

### 19.4 开发与必测矩阵

| 步骤 | 范围 | 通过条件 |
|---|---|---|
| R1 | 合同、端口、状态缓存、标准 Action 适配 | 正常 ACK/进度/结果关联，重复请求不重复执行 |
| R2 | Guard、租期、取消、执行端 watchdog | 超限被拒绝，停止不等待 worker，证据真实 |
| R3 | 与项目 A 合并完成真实抓放 | ROS 交接、Isaac 运动及物理判据完整 |
| R4 | 接入原始 Laya 后运行故障工况 | 选择来自真实模型，旧结果和错误不会误执行 |

| ID | 场景 | 必须观察的结果 |
|---|---|---|
| R01 | 原始 Laya 正常选择和实际抓放 | 候选到 ROS Goal 到物理结果可追踪，不能以规则回退充数 |
| R02 | 无解/无有效候选/窄间隙 | 明确拒绝或受限完成，无伪成功或关闭碰撞检查 |
| R03 | 超限、NaN、错误关节/起点 | 执行前拒绝；最终驱动限制仍有效 |
| R04 | 运动中取消 | 独立制动并保持，StopEvidence 对应本次命令 |
| R05 | Laya 超时、进程崩溃 | ROS 回调仍响应，不发新动作；未返回的选择失效 |
| R06 | 旧 Goal、旧评分晚到 | 旧 epoch/config/candidate 不能覆盖当前任务 |

watchdog 验收记录“过期到发起制动”，目标不超过一个配置控制周期；实际停稳时间与位移单列，不承诺瞬间停止。非实时 Linux 的超时也计入报告。

人工介入：用户查看一次执行中停止演示。停止或驱动限制没有证据时，不开启后续 Laya 物理执行；先反馈具体缺口。

## 20. 开发项目 T：一次小规模 Laya 微调

状态：PLAN ONLY。前置：项目 A/R 的基线与原始 Laya 实际 ROS 闭环通过。目标是证明本任务数据能完成一次微调与独立比较，不预设效果必然提高。

### 20.1 数据与固定版本

代码锁定 Laya `0.3.22` 对应 `6d942c92081fbc139e736bbd9ac0023223c29b7f`。复用 `convaiinnovations/laya` 的 `typed-decisions`，权重 revision 为 `55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851`，记录实装 hash；不自动路由或下载多个模型。官方材料见[固定版本 README](https://github.com/NandhaKishorM/laya/blob/6d942c92081fbc139e736bbd9ac0023223c29b7f/README.md)。

采集固定 100 个候选集，每组两条候选；按 100 个独立场景组划分训练/验证/测试 70/15/15。同种子、同布局及其连续帧只能在同一组。划分在训练前固定并保存 hash，不能看测试结果后重新分组。

从统一运行器保存 state/questions、候选摘要、版本、初始状态和实际执行结果。同一候选集的两条候选从相同初态分别执行；一条未执行或反馈不足时标 unknown，不自动算失败。场景复位属于数据采集，不代替抓取中的物理接触。

标签顺序固定：物理成功优先；两条都成功时依次比较放置误差和执行时间。误差差异不足 2 mm、时间差异不足 0.1 s 时按并列处理。两条都失败时标 replan。模型输入不能含执行后的结果、标签、最优候选标记或候选执行成功率。

输入结构沿用 `state + questions + gold`，按官方 notebook 实际 API 映射；不创建通用数据平台。仿真真值可生成标签，但不能替代 SENSOR 模型输入。

### 20.2 一次训练与一次独立测试

| 步骤 | 工作 | 完成条件 |
|---|---|---|
| T1 | 校验 100 组数据、分组、标签与 hash | 无跨集合场景泄漏，unknown 不伪标 |
| T2 | 冻结 encoder，训练 decision head | encoder 参数不更新；损失有限；产出一次训练记录 |
| T3 | 验证集选 checkpoint | 测试集不参与选 epoch、提示或阈值 |
| T4 | 比较 rule/原始 Laya/微调 Laya | 使用同一候选输入和独立测试集，报告完整结果 |
| T5 | 复用 ROS/Isaac 场景做微调后执行检查 | 选中 ID、实际使用模型、最终物理结果一致 |

初始训练配置：随机种子 20261001、最多 10 epochs、batch size 2、梯度累积 4、AdamW/head learning rate 1e-4；按验证损失保留最佳 checkpoint，连续 3 epochs 无改善提前停止。这是后续开发默认值，不是已测最佳参数。不开展超参数搜索。

训练时关闭 Isaac GUI。若显存不足，只降 batch 到 1；仍不足使用 CPU 完成小样本训练并报告耗时，不自动购买算力。推理性能必须在恢复 GUI 后另按第 17 节口径测量。

报告候选选择质量、replan/错误/超时率、物理成功率及延迟。由已采集候选结果计算的离线选择效用与在线真实执行成功率分开，不能把查表结果写成新一轮物理执行。

允许结果为“完成训练但未改善”。规则回退、原始模型和微调模型分别统计。100 组只证明小规模流程与初步效果，不证明泛化可靠性。

## 21. 开发项目 M：移动抓放与 GUI 演示

状态：PLAN ONLY。依赖：项目 A/R 的 SENSOR 单臂闭环；Laya 和微调能力按项目 L/T 分别记录，不以导航成功替代。

### 21.1 输入、输出与最小实现

输入为正式 Goal、目标颜色/已知几何、操作台区域、任务容差、RGB、LaserScan、odom/TF 和关节状态。输出为 Nav2 结果、停车证据、重新观察的场景快照、抓放结果和最终物理判据。

底盘使用履带外观加差速等效轮组，物理接触驱动；不逐帧写世界坐标。RGB＋2D 扫描的可观测性约束遵守第 5 节。Nav2 采用 Smac 2D 与 Regulated Pure Pursuit，近场速度保护复用 Collision Monitor。

首轮任务保持“导航 → 停稳 → 重观察 → 同台抓放 → 撤离”。操作台附近最多 3 个停车候选，拒绝后有限重试。移动时机械臂收拢，首版不携物跨区行驶。

### 21.2 开发步骤与故障处理

| 步骤 | 工作 | 验收 |
|---|---|---|
| M1 | 差速模型、雷达、odom/TF、Nav2 配置 | 3 个开发场景绕障到位，不读取随机障碍真值 |
| M2 | 顺序任务与资源约束 | 底盘未停稳不允许伸臂；导航后使用新观测 |
| M3 | 接入同一 EX Goal/Action、Ledger 和 B09 | 每步反馈/失败可关联，无第二套任务状态机 |
| M4 | 冻结 10 个可行种子和 2 个失败种子 | 正常场景至少 8/10 完成；失败场景正确结束 |
| M5 | GUI 中展示冻结场景及停止 | GUI 工况计入 M4，保留 RGB、雷达/代价地图和运行日志 |

导航封路或超时返回有原因的失败；不瞬移到操作台。目标观测不足则重观察一次，仍不足结束。底盘停车、机械臂执行、停止均依据反馈，不能仅靠固定 sleep。

上游暂不支持运行中追加独立动作轮次，因此每个宏动作完成并释放资源后再提交下一轮。一个抓放动作内部可包含多个有限阶段，但不能生成新的上游 Goal 或扩大原任务授权。
